Tavola

A studio for managing menus and wine lists, built for Terra Rossa, a UK venue run by Italian owners. The guest QR menu and the printed menu both come from a single source.

Role
Concept, design and engineering, solo
Client
Terra Rossa (La Cantina), United Kingdom
Delivered
Web and Android studio, QR menu, A3 print menu, operator console

Problem

The wine list changes constantly: vintages run out, glass and bottle prices shift, new labels arrive. Every change meant redoing the PDF and reprinting, and the online menu fell behind.

Goal

A tool the owners use on their own, in Italian, that keeps the QR menu and the printed menu in sync with no double work.

Process

  1. Step 1Understand the venueStart from the real list: how it is organised, who updates it, at what time of day.
  2. Step 2One data modelWines, drinks and dishes with glass and bottle prices, region and allergens: every view grows from here.
  3. Step 3A theme per venueThe studio stays neutral; the guest menu and print take on the venue’s identity, managed as a design system.
  4. Step 4From prototype to productReact and Node, from editor to print. Built for Terra Rossa, then opened by invitation to other venues.

From design to code

I designed and built Tavola on my own: research, identity, design system, frontend and backend. Every interface decision has a precise counterpart in the code.

One price, one source of truth

Editor and guest menu share the same formatting function: what the owner types is exactly what the guest reads.

// src/lib/format.js — shared by editor and guest menu
export const priceText = (it, cur = '£') => {
  const f = v => cur + v;
  if (it.wine && it.priceMode === 'gb')
    return (it.glass ? f(it.glass) : '—') + ' · ' + (it.bottle ? f(it.bottle) : '—');
  return it.single ? f(it.single) : '—';
};

No edit lost in silence

Saving waits until you stop typing and, if it fails, says so. Without a backend the app runs offline, on the device.

// src/lib/store.js
async save(d, onError) {
  if (api.apiEnabled()) {
    // debounce: no PUT on every keystroke
    clearTimeout(_saveTimer);
    _saveTimer = setTimeout(() => {
      api.saveState(d).catch(err => { if (onError) onError(err); });
    }, 700);
    return;
  }
  try { localStorage.setItem(KEY, JSON.stringify(d)); }
  catch (e) { if (onError) onError(e); } // quota full: say so
}

Accessibility in public digital services

Role
Design and coded prototyping
Context
Public-sector platforms at ZeroDD, confidential
Delivered
Three rebuilt, working patterns

I design to the AgID guidelines on the accessibility of IT tools and to the Designers Italia model.

In Italy, public digital services must comply with Law 4/2004 and the AgID guidelines, which refer to EN 301 549 and therefore to WCAG. That is the minimum, not the goal.

Behind every form is someone filling it in on their phone at lunch, someone using a screen reader, someone unfamiliar with bureaucratic language and short on time. I design for them, then check the criteria.

My public-sector projects are confidential. The components below are rebuilt from scratch with fictional data, and they really work.

Four recurring challenges

Bureaucratic language

Jargon and acronyms the office knows and the applicant doesn’t.

Dense tables

Hundreds of cases to filter and sort, often read with a screen reader.

Unclear statuses

Coloured dots as the only cue: invisible to anyone who can’t tell colours apart.

Long forms

Errors found only at the end, far from the field, and data lost when going back.

Case list

Status filters, sorting on every column and a result count announced by screen readers. Each status has an icon with its own shape, not just a colour.

AMF: from still life to looping on-model video

For a faux-fur fashion brand’s shop, I proposed opening every product with a silent clip a few seconds long: the garment worn, in motion, front and back in a single asset.

Role
Concept and visual design
Context
Redesign proposal for the AMF shop
Delivered
Concept, loop art direction, desktop and mobile rules

Problem

A garment on a hanger doesn’t show how it falls, how it opens, how long it is when worn. For a fur coat, that is exactly what drives the purchase.

Direction

On-model becomes the first read; still life drops to a detail. All within the AMF world: white, black, condensed type, no ornament.

Three decisions

  1. The garment is wornFront and back on the same white background, with consistent lighting across the shop.
  2. The loop replaces the poseA few seconds: the model walks in facing forward, half-turns and ends from behind. First and last frames match, so the loop is seamless.
  3. An addition, not a constraintWhere there is no video, the card shows the still on-model shot and reveals the still life on hover. The grid never breaks.

If it isn’t easy to use, it isn’t finished.

I put usability at the centre of every project. A product works when anyone understands it at first glance and uses it effortlessly, whatever their tools, their time or their abilities.

That doesn’t mean giving up on creativity. It means building it on solid foundations: clarity first, then character. When the most striking visual solution is also the clearest, the product doesn’t just work. It stays with you.

USABLE

  • clear
  • predictable
  • accessible
  • distinctive
  • expressive
  • crafted

ENGAGING

I don’t choose between clarity and character: I keep them together.together, not either/or

Usable, above all

Every choice starts from one question: can people do what they need, on the first try? I check it with prototypes and tests with real users, not opinions.

Within everyone’s reach

I design for people using a keyboard, a screen reader, an old phone, or with little time. Accessibility is a requirement from day one, not a check at the end.

Simple and intuitive

I remove until only the essential is left: fewer steps, everyday words, predictable behaviour. If an interface needs explaining, it needs redesigning.

Creative, without compromise

A clear interface can still move people. AMF’s loops are in motion, yet stop with a tap; Tavola’s style is warm, yet stays legible.

The method, in four beats

  1. UnderstandInterviews, observation, data analysis: people first, screens later.
  2. SimplifyFlows, information architecture, language. The shortest path to the goal.
  3. ShapeInterface and design system: tokens, components and documented rules.
  4. ValidateUsability testing, WCAG, keyboard and screen readers. Then repeat.
