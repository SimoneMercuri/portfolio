Problem

The wine list changes constantly: vintages run out, glass and bottle prices shift, new labels arrive. Every change meant redoing the PDF and reprinting, and the online menu fell behind.

Goal

A tool the owners use on their own, in Italian, that keeps the QR menu and the printed menu in sync with no double work.

Process

  1. Step 1Understand the venueStart from the real list: how it is organised, who updates it, at what time of day.
  2. Step 2One data modelWines, drinks and dishes with glass and bottle prices, region and allergens: every view grows from here.
  3. Step 3A theme per venueThe studio stays neutral; the guest menu and print take on the venue’s identity, managed as a design system.
  4. Step 4From prototype to productReact and Node, from editor to print. Designed for Terra Rossa, with themes that open it up to other venues.
User flow · UC-1

Marking a wine as sold out

The flow that drove design and development of the feature, including the decision that changes what the guest sees.

  1. StartThe owner opens the wine in the editor
  2. ActionTurns off a format: glass, bottle or both
  3. DecisionIs at least one format still on?
    • YesThe QR menu shows only the available format
    • NoThe wine is archived, restorable in one tap
  5. EndThe A3 list flags it among changes to print

Edge cases covered: a region left with no wines, a wine among the recommendations, two devices editing the same wine, a guest with the menu already open.

From analysis to specification

Before I design, I write. Here is an excerpt of the functional specification for a Tavola enhancement, as I delivered it in Confluence and then broke it down in Jira.

TAV-42Wine availability

  • Ready for development
  • Author: Simone Mercuri
  • v1.2

Starting requirement

“When a wine runs out, it has to disappear from the menu.”

The requirement, as a restaurant owner would put it

Ambiguities resolved before development

  1. 01 · Question

    Does “runs out” apply to the bottle, or to the glass as well?

    Decision

    Availability is set per format. A wine can be out by the glass and still available by the bottle.

  2. 02 · Question

    Does “disappear” apply to the A3 menu, which is already printed?

    Decision

    The QR menu updates immediately. The printed menu flags changes since the last print.

  3. 03 · Question

    What if a region is left with no wines?

    Decision

    The region heading is hidden too, and returns with the first available wine.

Use case UC-1 · Mark a wine as sold out

Actor
Venue owner
Precondition
The wine is published in at least one format
Postcondition
The format no longer shows in the QR menu; the wine stays in the archive

Main flow

  1. The owner opens the wine in the editor
  2. They switch off a format: glass, bottle or both
  3. The system saves and updates the QR menu
  4. The A3 menu lists the wine among changes to print

Edge cases

  • A guest has the menu open when the wine sells outThe wine stays visible until the next refresh, nothing vanishes under their finger
  • Two devices edit the same wineThe last edit wins; the other device sees a notice and reloads
  • The wine is among the recommendationsIt leaves the recommendations too, without leaving an empty slot
  • All formats switched offThe wine moves to the archive and can be restored in one tap

Acceptance criteria

Given a wine sold by the glass and by the bottle
When the owner switches off the glass
Then the QR menu shows only the bottle price
Given a region with a single available wine
When that wine sells out
Then the region no longer appears in the QR menu

One price, one source of truth

Editor and guest menu share the same formatting function: what the owner types is exactly what the guest reads.

// src/lib/format.js — shared by editor and guest menu
export const priceText = (it, cur = '£') => {
  const f = v => cur + v;
  if (it.wine && it.priceMode === 'gb')
    return (it.glass ? f(it.glass) : '—') + ' · ' + (it.bottle ? f(it.bottle) : '—');
  return it.single ? f(it.single) : '—';
};

No edit lost in silence

Saving waits until you stop typing and, if it fails, says so. Without a backend the app runs offline, on the device.

// src/lib/store.js
async save(d, onError) {
  if (api.apiEnabled()) {
    // debounce: no PUT on every keystroke
    clearTimeout(_saveTimer);
    _saveTimer = setTimeout(() => {
      api.saveState(d).catch(err => { if (onError) onError(err); });
    }, 700);
    return;
  }
  try { localStorage.setItem(KEY, JSON.stringify(d)); }
  catch (e) { if (onError) onError(e); } // quota full: say so
}
